# IssueFlow architecture

## Frontend

A framework-free JavaScript ES-module application. `assets/core.js` holds pure task validation, KPI calculation, filtering and CSV logic. `assets/app.js` renders the dashboard, handles accessible dialogs, manages drag-and-drop and delegates persistence to either localStorage or `assets/cloud.js`.

## Offline demo

The app works without credentials. A seeded ten-issue workspace lives in localStorage, with backup/restore for reproducibility. The PWA service worker caches only app-shell assets. The browser remains responsible for guest storage.

## Cloud collaboration

Optional Supabase integration uses GitHub OAuth and a PostgreSQL schema with four tables: workspaces, members, issues, events. All four tables enable RLS. `issueflow_is_member()` enforces workspace membership on select and mutations. `issueflow_create_workspace()` and `issueflow_join_workspace()` establish membership atomically. Random 32-character invite codes are bearer credentials and should be treated as private.

Issue IDs in cloud mode are generated by PostgreSQL bigint identity, which prevents two users simultaneously creating the same issue number. The frontend refreshes the active workspace every ~12 seconds while visible. Guest and cloud data are not mixed.

### Tradeoffs

Cloud availability is limited by Supabase's free-tier service levels and pauses. GitHub OAuth requires external provider setup. There is no offline cloud write queue, granular project roles, push-based realtime or formal enterprise security audit. Activity entries are useful collaboration context, not tamper-proof compliance logs. Never expose database or OAuth secrets in the website.

## Progressive web app

`manifest.webmanifest` provides installability metadata and branded icons. `service-worker.js` caches the static shell but never intercepts external Supabase API/auth requests. It does not cache credentials or private user records.

## Tests

`node --test tests/*.test.mjs` runs pure application logic and cloud data-conversion tests. Full RLS integration needs an actual Supabase project with at least two distinct GitHub users and must be checked before broad public adoption.
